# Part 3: Programming (25%)

Implement the measurement pipeline from the paper, then audit some code you
inherited.

## Constraints

- **Python 3.9+, standard library only.** No numpy, scipy, sklearn, pandas.
- Budget about an hour and a quarter. If you are over that, skip the stretch
  items and say so in `RESULTS.md`; we would rather see the audit done well.
- No network access, no GPU, no API keys, no downloads. Everything runs on a
  laptop in under a second.
- Work in `code/`. Submit that whole directory.

The no-libraries rule is not hazing. `sklearn.metrics.roc_auc_score` is one line
and we already know you can call it. We want to see whether you get the tie
handling right, which is the part that actually bites on this data.

## The data

`data/generations.json` holds 300 examples. Each has a question, 10 sampled
generations with per-token log probabilities, a 10x10 directed entailment
matrix, and a binary `is_hallucination` label.

`data/toy_cases.json` holds four small hand-checkable cases with known answers.

The data is **synthetic**, generated by `tools/generate_fixtures.py`, which
documents the process. It is not real model output. That does not matter for
anything you are asked to do, and we would rather tell you than have you assume
otherwise.

Fields beginning with `_` are latent ground truth, included so the fixtures can
be audited. **Do not use them in Tasks 1 to 3.** Task 6 uses them explicitly.

## Task 1: Semantic clustering

Implement `cluster_by_entailment` in `semantic_entropy.py`.

The entailment relation is directed, noisy, and **not transitive**. Two
generations cluster together when they entail each other in both directions.
Because the relation is not transitive, the answer depends on processing order,
so the docstring pins an exact convention. Follow it exactly, even where you
think another convention is better. Task 5 is where you tell us what you think.

## Task 2: Entropy estimators

Implement `discrete_semantic_entropy`, `logsumexp`, `sequence_logprob`, and
`length_normalized_logprob`. Everything is in nats. Three of these are a few
lines each.

`logsumexp` must stay finite for realistic long-form log probabilities. The
public tests include a case a naive implementation fails, and the fix is one
standard trick.

**[stretch]** `cluster_log_probabilities` and `weighted_semantic_entropy` are
optional. Skip them if you are short on time: the driver prints `skipped` for
those scores and the tests covering them skip cleanly. Skipping costs you
nothing on the core score.

## Task 3: AUROC

Implement `auroc` from scratch. Ties get half credit, which matters here: the
discrete semantic entropy of 10 samples takes only 28 distinct values across the
300 examples, so tied scores are the normal case rather than an edge case.

**The docstring gives you the algorithm step by step**, including the rank-sum
formula, and tells you a brute-force double loop is equally acceptable. You are
not being asked to invent anything, only to handle ties carefully.

Return `float('nan')` when only one class is present.

## Task 4: Run it and report

Run `python3 semantic_entropy.py`. In a short `RESULTS.md`, a few paragraphs at
most:

1. The AUROC values you got.
2. `num_clusters` is a cruder score than `discrete_se`: it throws away the
   cluster proportions. Compare their AUROCs and say what the difference buys.
3. One paragraph: is any of this good enough to deploy as a filter that
   withholds answers? Use a number, not an adjective. Problem 4(a) in Part 2 is
   relevant.

Do not write more than that. We are looking for interpretation, not volume.

**[stretch]** If you have time, compare `weighted_se_joint` against
`weighted_se_normed`. They differ only in whether sequence log probability is
length-normalised. Which wins here, and what would you need to know to say
whether that generalises?

## Task 5: Audit `buggy_metrics.py`

That module was written by a previous contributor, is imported by downstream
code, and its output has been quoted in an internal write-up. It has not been
carefully reviewed.

**It contains more than one defect.** We are not telling you how many.

Write `AUDIT.md`. For each defect:

- Where it is, and what is wrong
- A concrete input where it produces a wrong answer, with the correct value
- Whether it fails loudly or silently, and roughly who would notice
- Severity, and why

Then, for each, add a regression test to `tests/` that fails against the
original and passes against your fix. Fix them.

We care most about the reasoning. A defect you found, explained precisely, and
covered with a test that genuinely discriminates is worth more than three
one-line "this is wrong" notes.

One of the defects barely moves the aggregate number on this dataset. It is
still a defect. If you notice that and have something to say about it, say it.

## Task 6 [stretch]: Which way is the estimate wrong?

Two effects push the estimated semantic entropy in opposite directions:

- The plug-in entropy estimator is **negatively** biased at `N = 10`
  (Part 2, Problem 2).
- A noisy entailment oracle splits clusters that should be merged, which pushes
  the estimate **up** (Part 2, Problem 3(d) and 3(e)).

Using `_latent.true_entropy_nats` as ground truth, measure the net bias on the
300 examples empirically. Report the sign and size, say which effect dominates,
and confirm it against the theory from Part 2. If measurement and theory
disagree, say so and investigate rather than picking whichever you prefer.

Put this in `RESULTS.md`.

## Running things

```bash
cd code
python3 -m unittest discover tests -v
python3 semantic_entropy.py
```

The public tests are a self-check, not the grading set. Passing them all means
your code is not obviously wrong. We run additional tests, including ones that
check the clustering convention and numerical stability at magnitudes the public
tests do not reach.

## What we are scoring

- **Correctness** on the hidden tests.
- **The audit.** Depth of reasoning, and whether your tests really discriminate.
- **Judgement** in Task 4. Numbers with an interpretation, not numbers alone.
- **Code you would not mind someone else maintaining.** Clear over clever. We
  are not counting lines or grading style beyond readability.
